## 1. Summary

**What you asked for and what this design delivers**

| Feature named in the requirement | This design |
|---|---|
| "Warranty Eligible" checkbox on Released products, with a provision % (default 3.50%) | Builds it |
| Warranty posting setup: item group → warranty expense account (debit) and warranty provision liability account (credit) | Builds it (new setup page under General ledger > Posting setup) |
| Automatic, balanced warranty voucher lines during sales invoice posting for each eligible line | Builds it |
| Financial dimensions taken from the invoice line; accounting and reporting currency amounts at the invoice exchange rate | Builds it |
| Automatic exact reversal when a sales credit note is posted for a warranty item | Builds it |
| Posting stops with a setup error when the warranty setup is missing (AC-03) | Builds it |
| Voucher linked to the invoice (AC-01) | Builds it. The warranty lines post under the invoice's own voucher number, so the standard Voucher transactions page of the posted invoice shows them |
| Separate warranty voucher number ("WAR-000492" in Figure 1) | Replaced by the invoice's own voucher number, as you confirmed |

When a sales invoice is posted (this includes invoices for project sales orders), the system checks each invoice line. If the item is marked **Warranty eligible**, it calculates *line net amount (excluding sales tax, after line discount) × provision %*. It then adds two lines to the invoice's own voucher, with the invoice's voucher number and date:
- a debit to the warranty expense account;
- a credit to the warranty provision liability account.

Both accounts come from the new **Warranty posting setup** for the item's item group, combined with the invoice line's financial dimensions. The two lines use the same transaction currency and the same exchange rates (accounting and reporting) as the invoice line's revenue.

On a credit note the line amount is negative, so the same logic posts the exact opposite entry: debit liability, credit expense. When the credit note is linked to the original invoice line, the original line's provision % is used. If an eligible item's item group has no setup, the whole invoice posting is cancelled with a clear error.

## 2. Scope and assumptions

In scope:
- sales order invoices and sales order credit notes, posted through Sales order > Invoice, including project sales orders;
- the new Released product fields;
- the setup page and its security;
- a log of the provision posted per invoice line.

Decided with the client: **the warranty lines post in the sales invoice's own voucher, with the invoice's voucher number and date.** No separate "WAR-" number sequence or second voucher is created. The lines are posted, or rolled back, together with the invoice. They appear on the posted invoice's Voucher transactions page.

Assumptions (please correct them if any is wrong):
1. **Free text invoices, project invoices (Project management > invoice proposals) and intercompany documents other than sales orders are out of scope.** The FRD names "Sales Invoice Posting" only.
2. "Net invoice revenue" is the invoice line's net amount excluding sales tax and after line discount, which is the amount posted to the revenue account. Miscellaneous charges, total discount and cash discount are not included.
3. The warranty amount is calculated in the invoice currency and rounded to that currency's rounding. Accounting and reporting currency amounts are converted with exactly the exchange rates that the invoice line's revenue uses. Fixed rates, the exchange rate date and the settlement rules are included.
4. The provision % is read from the released product when the invoice is posted. If the % changes later, invoices already posted do not change.
5. **Credit notes**: when the credit note line refers to the original invoice line (the standard return / "Find sales order" link), the system reverses with the % used on that original invoice. If the original invoice had no warranty posted (for example, it was posted before go-live), nothing is reversed. When a credit note line has no link to an original invoice (for example, a manually entered negative line), the item's current % applies.
6. The accounts are taken from the current warranty posting setup, also for credit notes.
7. An item with **Warranty eligible = Yes** must have a provision % above 0 and no more than 100. When the flag is switched on and the % is empty, it is filled with 3.50. New released products get 3.50 as their default %, with the flag set to No. Existing products keep the flag at No, and the business must mark them.
8. Invoice posting stops with an error, and nothing of that invoice is posted (AC-03), when an eligible item:
   - has no item group; or
   - has an item group with no setup line that holds both accounts.
9. Pro forma invoices post nothing to the ledger in standard, so they post no warranty lines either.
10. Released product fields are company-specific (they live on the released product). The warranty posting setup is per legal entity.
11. The two new lines get the new posting types "Warranty expense" and "Warranty provision". Their voucher line descriptions follow Figure 1:
    - expense line: "Warranty accrual - <invoice number>";
    - liability line: "Warranty reserve - <invoice number>".
12. The FRD's menu path calls the page "Warranty posting profiles". This design names it **Warranty posting setup**, as in the FRD's functional rules.

Figure 1 is an accounting flow diagram that shows the resulting voucher. It is not a printed report or a screen to be built, so no layout is designed. The voucher shows in the standard Voucher transactions page. The account numbers, amounts and voucher number in the figure are sample content.

## 3. Functional design

### 3.1 Released products
On **Product information management > Products > Released products**, **Sell** FastTab, a new group **Warranty provision** holds:
- **Warranty eligible** (Yes/No, default No)
- **Warranty provision %** (default 3.50, two decimals)

### 3.2 Warranty posting setup
**General ledger > Posting setup > Warranty posting setup** is a simple list with one line per item group:

| Field | Meaning |
|---|---|
| Item group | Item group (mandatory, unique) |
| Warranty expense account | Main account, debit side on invoices |
| Warranty provision account | Main account (liability), credit side on invoices |

Both accounts are mandatory and are chosen with the standard main account lookup. Financial dimensions are not entered here: they always come from the invoice line.

### 3.3 Posting a sales invoice
For each invoice line that posts to the ledger:
1. If the item is not warranty eligible, nothing changes.
2. Otherwise, the system finds the setup for the item's item group. If it is missing, posting stops with: *"Warranty posting setup is missing for item group %1 (item %2). Set it up under General ledger > Posting setup > Warranty posting setup."*
3. Warranty amount = round(line net amount × provision % / 100). If the result is 0, nothing is posted.
4. Two lines are added to the invoice voucher, under the invoice's voucher number and date:

| Posting type | Account | Debit | Credit | Text |
|---|---|---|---|---|
| Warranty expense | expense account + line dimensions | amount | | Warranty accrual - invoice no. |
| Warranty provision | provision account + line dimensions | | amount | Warranty reserve - invoice no. |

Example (AC-01): a USD 40,000.00 line at 3.50% gives a debit of 1,400.00 to the expense account and a credit of 1,400.00 to the provision account, in the invoice's voucher.

5. A log record is written with the invoice line, voucher, date, % and amounts. The credit note reversal uses it to reverse the exact amount.

### 3.4 Posting a credit note
The same steps apply. The line amount is negative, so the expense line becomes a credit and the provision line a debit, in the credit note's own voucher. When the credit note is linked to the original invoice line, the % comes from that line's log record (assumption 5).

## 4. Technical design

All objects are created in model **DYLOExtensions**. The descriptor references these modules: ApplicationSuite, ApplicationFoundation, ApplicationPlatform, Ledger, SourceDocumentationTypes, Currency, Dimensions. ### 4.1 Data model

**EDT `DYLO_WarrantyProvisionPct`**: Real, extends `Percent`. Label "Warranty provision %".

**Table extension `InventTable.DYLO_Extensions`** adds these fields:

| Field | Type | Notes |
|---|---|---|
| DYLO_WarrantyEligible | NoYes | Label "Warranty eligible" |
| DYLO_WarrantyProvisionPct | DYLO_WarrantyProvisionPct | |

Field group `DYLO_WarrantyProvision` holds both fields.

**Class extension `InventTable_DYLO_Extension`** (`[ExtensionOf(tableStr(InventTable))]`, CoC):
- `initValue()`: after `next`, set `DYLO_WarrantyProvisionPct = 3.50` (use a constant `DYLO_WarrantyDefaultPct`).
- `modifiedField(FieldId _fieldId)`: after `next`, if `DYLO_WarrantyEligible` changes to Yes and the % is 0, set the % to 3.50.
- `validateWrite()`: after `next`, if the item is eligible and the % is ≤ 0 or > 100, show an error and return false.

**Table `DYLO_WarrantyPostingSetup`**: company-specific, table group Parameter, clustered unique index `ItemGroupIdx` on ItemGroupId.

| Field | EDT | Mandatory |
|---|---|---|
| ItemGroupId | ItemGroupId (relation to InventItemGroup) | Yes |
| ExpenseLedgerDimension | LedgerDimensionDefaultAccount (relation to DimensionAttributeValueCombination) | Yes |
| ProvisionLedgerDimension | LedgerDimensionDefaultAccount (relation to DimensionAttributeValueCombination) | Yes |

- Methods: `static find(ItemGroupId, boolean _forUpdate = false)` and `static exist(ItemGroupId)`.
- Delete actions: none. InventItemGroup is not changed. If an item group is deleted, its setup line stays but is never found.

**Table `DYLO_WarrantyProvisionTrans`**: company-specific, table group Transaction. It is the posting log.

| Field | EDT |
|---|---|
| CustInvoiceTransRecId | RefRecId (relation to CustInvoiceTrans.RecId), unique index |
| InvoiceId | InvoiceId |
| InvoiceDate | InvoiceDate |
| Voucher | Voucher (the invoice's own voucher) |
| ItemId | ItemId |
| ProvisionPct | DYLO_WarrantyProvisionPct |
| AmountCur | AmountCur |
| CurrencyCode | CurrencyCode |
| ExpenseLedgerDimension | LedgerDimensionAccount (merged, with dimensions) |
| ProvisionLedgerDimension | LedgerDimensionAccount (merged, with dimensions) |

Only posting writes to this table, and users cannot edit it. It has no form: the voucher lines are the auditable entries.

**Enum extension `LedgerPostingType.DYLO_Extensions`**: `LedgerPostingType` (model SourceDocumentationTypes) has `IsExtensible = true`. Add two values:
- `DYLO_WarrantyExpense` ("Warranty expense");
- `DYLO_WarrantyProvision` ("Warranty provision").

### 4.2 Business logic

**Hook point (verified in 10.0.49 source, `ApplicationSuite\Foundation\AxClass\SalesInvoiceJournalPostBase.xml`)**

`SalesInvoiceJournalPostBase` (ApplicationSuite) is an abstract public class that extends `FormletterJournalPost`. Three members are used:
- `protected void postLine()` is marked `[Hookable]` and is not final.
  - `FormletterJournalPost` calls it once per journal line, and only when `canPostLedger()` is true.
  - `SalesInvoiceJournalPost` and `SalesInvoiceJournalPostProj` override it and call `super()`, so wrapping the base class covers both.
- `protected LedgerVoucherTransObject createLedgerVoucherTransObject(LedgerVoucherObject, LedgerDimensionAccount, AmountCur, CurrencyExchangeHelper)` is called only from `postLine`.
  - It receives the exchange-rate helper that holds the invoice's fixed accounting, secondary and reporting rates.
  - The method that computes the reporting rate (`reportingCurrencyFixedExchangeRate`) is `internal`, so our model cannot call it. Capturing the helper here gives exactly the same rates without calling it.
- Accessible state, protected members of the class: `custInvoiceJour`, `custInvoiceTrans`, `salesParmLine`, `lineValue`, `ledgerVoucher` (from `FormletterJournalPost`), `this.currencyCode()`, `this.fixedExchRate()`, `this.fixedExchRateSecondary()`.

`ledgerVoucher` is the invoice's own voucher, and its number and date are the invoice's. Lines added to it get the invoice's voucher number, as the client confirmed. No number sequence and no second `LedgerVoucherObject` are created.

**Class extension `SalesInvoiceJournalPostBase_DYLO_Extension`** (`[ExtensionOf(classStr(SalesInvoiceJournalPostBase))] final class`):
- Member: `CurrencyExchangeHelper dyloRevenueExchangeRateHelper;`
- `createLedgerVoucherTransObject(...)`: set `dyloRevenueExchangeRateHelper = _exchangeRateHelper;`, then `return next createLedgerVoucherTransObject(...)`.
- `postLine()`: set `dyloRevenueExchangeRateHelper = null`, call `next postLine()`, then:
  ```
  DYLO_WarrantyProvisionPostingService::construct(
      ledgerVoucher, custInvoiceJour, custInvoiceTrans, salesParmLine,
      lineValue, this.currencyCode(), this.dyloExchangeRateHelper()).post();
  ```
- `dyloExchangeRateHelper()` (private) returns the captured helper.
  - It may find none: the Russian goods-in-route branch posts no revenue line.
  - In that case it builds a helper the same way `postLine` does: `CurrencyExchangeHelper::newExchangeDate(Ledger::primaryLedger(CompanyInfo::findDataArea(curExt()).RecId), ledgerVoucher.findLedgerVoucherObject().parmAccountingDate())`, then `parmExchangeRate1(this.fixedExchRate())` and `parmExchangeRate2(this.fixedExchRateSecondary())`.
- Posting runs inside the invoice's transaction. If the service throws an error, the whole invoice is rolled back (AC-03).

**Class `DYLO_WarrantyProvisionPostingService`** (new; `construct` takes the parameters above; `post()` does the work):
1. `InventTable item = custInvoiceTrans.inventTable();` Return if the line has no item, or if `item.DYLO_WarrantyEligible == NoYes::No`.
2. Determine the %:
   - If `salesParmLine.salesLine().InventTransIdReturn` is filled, find the original `CustInvoiceTrans` whose `InventTransId` equals it.
     - If the original line has a `DYLO_WarrantyProvisionTrans` record, use its `ProvisionPct` (when there are several, take the latest by InvoiceDate).
     - If the original line is found but has no log record, return: there is nothing to reverse.
   - Otherwise use `item.DYLO_WarrantyProvisionPct`.
3. `ItemGroupId groupId = item.itemGroupId();` and `setup = DYLO_WarrantyPostingSetup::find(groupId)`. If no setup is found, or either account is 0, `throw error(strFmt("@DYLOExtensions:WarrantySetupMissing", groupId, item.ItemId))`.
4. `AmountCur amount = CurrencyExchangeHelper::amount(_lineValue * pct / 100, _currencyCode);` Return if the amount is 0.
5. Build the two accounts with dimensions:
   - `DimensionDefault dim = custInvoiceTrans.DefaultDimension;`
   - `expenseDim = LedgerDimensionFacade::serviceCreateLedgerDimension(setup.ExpenseLedgerDimension, dim);`
   - `provisionDim`: the same call with `setup.ProvisionLedgerDimension`.
6. Add the two voucher lines:
   - `LedgerVoucherObject lvo = _ledgerVoucher.findLedgerVoucherObject();` This is the invoice's voucher object, so the lines carry the invoice's voucher number and date.
   - Expense line: `LedgerVoucherTransObject::newTransactionAmountDefault(lvo, LedgerPostingType::DYLO_WarrantyExpense, expenseDim, _currencyCode, amount, _exchangeRateHelper)`.
   - Provision line: `LedgerVoucherTransObject::newTransactionAmountDefault(lvo, LedgerPostingType::DYLO_WarrantyProvision, provisionDim, _currencyCode, -amount, _exchangeRateHelper)`.
   - On each line, set `parmText(strFmt(...))` with label `@DYLOExtensions:WarrantyAccrualTxt` (expense) or `@DYLOExtensions:WarrantyReserveTxt` (provision) and `custInvoiceJour.InvoiceId`. Set `parmSourceTableId` / `parmSourceRecId` to `custInvoiceTrans` where available.
   - Call `_ledgerVoucher.addTrans(...)` for both lines.
   - Both lines use the same helper and opposite amounts, so they balance in transaction, accounting and reporting currency.
7. Insert a `DYLO_WarrantyProvisionTrans` record: CustInvoiceTransRecId = `custInvoiceTrans.RecId`, Voucher = `custInvoiceJour.LedgerVoucher`, plus the other fields listed in 4.1.

### 4.4 Security
- Privileges:
  - `DYLO_WarrantyPostingSetupMaintain`: menu item, Delete access.
  - `DYLO_WarrantyPostingSetupView`: menu item, Read access.
- Duty `DYLO_WarrantyPostingSetupMaintain`: holds both privileges.
- Role `DYLO_WarrantyPostingSetupManager` ("Warranty posting setup manager"): holds the duty. Assign it to financial controllers and GL accountants. Administrators can also add the duty to existing roles.
- The released product fields are covered by the existing privileges of the Released products form.
- Posting runs under the invoicing user's existing rights. Users do not need access to the setup page to post.

## 5. Setup and data
1. Assign the role **Warranty posting setup manager** to the users who maintain the setup.
2. Open **General ledger > Posting setup > Warranty posting setup**. Add one line per item group of warranted goods, with the expense account (for example 614500) and the liability main account (for example 218900).
3. Open **Released products**. On each warranted item, set *Warranty eligible* = Yes and check the % (3.50 by default).
4. No number sequence is needed: the warranty lines use the invoice's voucher number.
