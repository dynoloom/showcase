# TDD – REQ-INT-508 Inbound Sales Order API with Payload Tracing & Reprocessing Form

## 1. Summary

**What you asked for and what this design delivers**

| Feature named in the FRD | This design |
|---|---|
| Real-time sales order creation API (JSON in, JSON out) | Built: a custom JSON service |
| Idempotency / duplicate prevention by External Order Reference | Built |
| Business validation (customer active and not blocked for invoicing, items exist and are released, quantity > 0) | Built |
| Structured synchronous JSON response (status, Sales ID, Correlation ID, errors) | Built |
| Mandatory trace logging of every call (request, response, timestamp, duration, user) | Built |

| "Reprocess Failed Order" button (failed records only) | Built |
| Purge of successful records older than 90 days, failed records kept | Built |
| Toolbar buttons "Refresh" and "View JSON Payload" from the mockup | Built (Refresh is the standard form refresh; View JSON Payload opens a larger viewer) |
| Filter bar (text filter, status filter with counts) from the mockup | Built |

| Mockup's dark-blue header on the details pane, pink error box, grey JSON boxes | Covered by the standard D365 look, as you agreed: these areas use the normal D365 theme |

External systems (e-commerce portals, B2B platforms, CRM) call one REST endpoint and send an order as JSON. D365 checks the order and creates an open sales order with its lines. It then answers immediately with the Sales ID, or with readable errors. Every call is written to a trace log.

Support staff work with the log in a new inquiry form under **Sales and marketing > Inquiries and reports > Integration > Sales Order API Trace Log**. There they can:
- read the request, the response and the error;
- reprocess a failed call after fixing the master data;
- purge old successful records.

Everything is built in the new model **DYLOExtensions**, using only new objects and extensions. No standard object is overlayered.

## 2. Scope and assumptions

**In scope:** the service and its contracts, the order validation and creation logic, the trace table, the trace log form and the payload viewer, reprocessing, purging, the menu entry, security and labels.

**Out of scope:** setting up the external systems, registering their Microsoft Entra ID applications, and anything after order creation (confirmation, picking, invoicing).

**Assumptions** (correct any that are wrong):

1. **Legal entity.** The payload may carry an optional `legalEntity` (for example "USMF"). When it is missing, the order is created in the default company of the D365 user mapped to the calling application. The trace record is saved in the company where the order is created, or would have been created.
2. **Caller identity.** Each external system connects with its own Microsoft Entra ID application, mapped to a D365 user (System administration > Setup > Microsoft Entra ID applications). That D365 user is logged as the caller. The raw client ID is not available to X++, so it is not logged.
3. **"Active and not blocked for invoicing"** means the customer exists in the legal entity and its *Invoicing and delivery on hold* (Blocked) value is neither **Invoice** nor **All**. D365 has no separate "active" flag for customers.
4. **"Released in the target legal entity"** means the item has a released product record (InventTable) in that legal entity. The design also rejects items whose sales order settings are **Stopped**, which covers the FRD's "discontinued item".
5. **Field mapping:**
   - Customer PO Reference → *Customer requisition* (SalesTable.PurchOrderFormNum).
   - Requested Ship Date → *Requested ship date* on the header and on every line.
   - Currency → order currency. When it is missing, the customer's currency is used.
   - Unit of measure → the sales unit. When it is missing, the item's default sales unit is used.
   - Site/Warehouse → the line's site and warehouse. When either is missing, the D365 default from the customer and item applies.
   - Unit Price override → when it is given, it replaces the price found by D365 (price unit 1). Line discounts from trade agreements still apply.
6. **Stored request JSON.** The stored request is the request as D365 received and read it, written back out as JSON. Members that D365 does not know are not stored. The JSON is stored and shown indented ("formatted").
7. **Duplicates.** Take a repeated External Order Reference whose earlier call succeeded (status Success or Reprocessed). As long as that sales order still exists, the call returns the original Sales ID. The repeated call is itself logged as a Success record, with `"duplicate": true` in its response. If the original order was deleted, a new one is created.
8. **Reprocessing** updates the same trace record.
   - On success: status becomes Reprocessed, Sales ID is filled, Retry Count goes up by 1, and the new response and the time of the retry are stored.
   - On failure: status stays Failed, Retry Count goes up by 1, and the error and response are replaced with the new ones.
   - Reprocessing also runs the duplicate check.
9. **Purge** deletes only records with status **Success** that are older than 90 days, counted from the execution time. Failed and Reprocessed records are kept for audit. 90 days is the default in the purge dialog. The purge can also run as a recurring batch job.
10. **Screen look (agreed with you).**
    - The form uses the standard D365 look throughout.
    - Only the Status column is coloured: green for Success, red for Failed, amber for Reprocessed.
    - The mockup's dark-blue header of the details pane, its pink error box with red text and its grey JSON boxes are shown in the normal D365 theme. The JSON text uses the standard font, not a monospaced one.
11. **Mockup elements not built.**
    - The dark top bar ("Finance and Operations", "USMF", "Admin | Integration Monitor") and the breadcrumb are the standard D365 shell, not part of the form.
    - The red arrow and the "Selected Failed Record" call-out are annotations, and the IDs, names and dates in the mockup are sample data. None of these is built.
12. **Counts in the filter bar** ("All (142) · Success (136) · Failed (6)") count the records of the current legal entity. A Reprocessed count is added.

## 3. Functional design

### 3.1 API call

The external system POSTs to:
`https://<environment>/api/services/DYLO_SalesOrderApiServices/DYLO_SalesOrderApiService/createSalesOrder`

Request body:

```json
{ "_request": {
    "correlationId": "COR-98413",
    "externalOrderId": "WEB-77411",
    "legalEntity": "USMF",
    "customerAccount": "US-004",
    "currency": "USD",
    "requestedShipDate": "2026-11-20",
    "customerPoReference": "PO-5531",
    "lines": [ { "itemId": "D0001", "qty": 5, "unit": "ea", "site": "1", "warehouse": "11", "unitPrice": 12.50 } ] } }
```

Response:

```json
{ "status": "Success|Failed", "success": true, "salesId": "SO-001402", "correlationId": "COR-98413",
  "externalOrderId": "WEB-77411", "duplicate": false, "errorCode": "", "message": "", "errors": [] }
```

Processing:
1. Start the timer and read the request.
2. Check the request:
   - correlationId, externalOrderId and customerAccount are present;
   - there is at least one line.
   - If either check fails, the error code is PAYLOAD_INVALID.
3. Run the duplicate check. If it finds a match, answer with the existing Sales ID.
4. Apply the validation rules. All errors are collected and all are returned:

   | Check | Error code |
   |---|---|
   | Legal entity exists | LE_NOT_FOUND |
   | Customer exists | CUST_NOT_FOUND |
   | Customer is not blocked for Invoice or All | CUST_BLOCKED |
   | Currency exists | CURRENCY_NOT_FOUND |
   | Every item is released | ITEM_NOT_FOUND |
   | Every item is not stopped for sales | ITEM_STOPPED |
   | Every quantity > 0 | QTY_INVALID |
   | Unit exists and converts to the item's inventory unit | UNIT_INVALID |
   | Site exists | SITE_NOT_FOUND |
   | Warehouse exists and belongs to the site | WAREHOUSE_INVALID |

   When any rule fails:
   - `errorCode` is the first error code;
   - `message` joins all the messages, for example "Validation Failed: Customer account 'US-099' does not exist in legal entity USMF.";
   - `errors` lists every message.
5. Create the header and lines in one transaction. If D365 itself refuses (for example in its own checks in `validateWrite`, or in a credit limit check), everything is rolled back. The infolog text is returned with code CREATE_FAILED.
6. Write the trace record and return the response. The HTTP status is always 200; the outcome is in `status` and `success`.

### 4.3 Service and contracts

All contracts are `[DataContractAttribute]` classes with `[DataMemberAttribute('<jsonName>')]` parm methods.

- **DYLO_SalesOrderApiRequestContract** members:
  - correlationId, externalOrderId, legalEntity, customerAccount, currency;
  - requestedShipDate (TransDate);
  - customerPoReference;
  - lines: a List of DYLO_SalesOrderApiLineContract, declared with `[AifCollectionTypeAttribute('_lines', Types::Class, classStr(DYLO_SalesOrderApiLineContract))]` on its parm method.
- **DYLO_SalesOrderApiLineContract** members:
  - itemId, qty (Qty), unit, site, warehouse;
  - unitPrice (Price);
  - hasUnitPrice (boolean). The parm method sets it when unitPrice is assigned, so a price of 0 is told apart from "not sent".
- **DYLO_SalesOrderApiResponseContract** members:
  - status (str), success (boolean), salesId, correlationId, externalOrderId, duplicate (boolean), errorCode, message;
  - errors: a List of str, with AifCollectionTypeAttribute Types::String.

**Class DYLO_SalesOrderApiService** (public) has one operation:
`public DYLO_SalesOrderApiResponseContract createSalesOrder(DYLO_SalesOrderApiRequestContract _request)`
1. Starts a `System.Diagnostics.Stopwatch` and records `DateTimeUtil::utcNow()`.
2. Serializes `_request` with `FormJsonSerializer::serializeClass` (ApplicationPlatform), then formats it with `DYLO_JsonFormatter::format`.
3. If `legalEntity` is given and `DataArea::exist` is true, runs the rest inside `changecompany(legalEntity)`. An unknown legalEntity gives LE_NOT_FOUND, logged in the caller's company.
4. Calls `DYLO_SalesOrderApiProcessor::process(_request)`, which returns the response contract.
5. Calls `DYLO_SalesOrderApiTraceLogger::logCall(...)` with:
   - the request JSON;
   - the response JSON (serialized and formatted);
   - the duration, the status and the errors.
6. Returns the response.

The service method catches every unexpected exception, including CLRError, and UpdateConflict or Deadlock after the retries are used up. Each one becomes a Failed response with errorCode UNEXPECTED, which is logged, so every call is traced.

**DYLO_SalesOrderApiProcessor** is used by both the service and reprocessing. `static process(request)` runs three steps in turn: the payload check, the duplicate check, then validation (DYLO_SalesOrderApiValidator) and creation (DYLO_SalesOrderApiOrderCreator). It builds the response contract.

**AxService DYLO_SalesOrderApiService:**
- Class DYLO_SalesOrderApiService, operation createSalesOrder.
- External name DYLO_SalesOrderApiService.

**AxServiceGroup DYLO_SalesOrderApiServices:**
- Contains DYLO_SalesOrderApiService.
- AutoDeploy = Yes.

### 4.4 Validation – class DYLO_SalesOrderApiValidator

`public List validate(DYLO_SalesOrderApiRequestContract _request)` returns a list of `[errorCode, message]` containers. An empty list means the request is valid.

- **Customer:** `CustTable::find(customerAccount)`.
  - Not found → CUST_NOT_FOUND.
  - `Blocked == CustVendorBlocked::Invoice || Blocked == CustVendorBlocked::All` → CUST_BLOCKED.
- **Currency:** when given, `Currency::exist(currency)` must be true → otherwise CURRENCY_NOT_FOUND.
- **Per line:**
  - `InventTable::find(itemId)` must exist → ITEM_NOT_FOUND.
  - `InventItemSalesSetup::find(itemId, InventDim::inventDimIdBlank()).isStopped()` → ITEM_STOPPED. When a site is given, the site-specific record is checked too.
  - `qty > 0` → QTY_INVALID.
  - The unit symbol must exist (`UnitOfMeasure::findBySymbol`) and convert to the item's inventory unit, checked with `EcoResProductUnitConverter::canBeConvertedGivenUnitSymbolsForReleasedProduct(itemId, InventDim::inventDimIdBlank(), unit, InventTableModule inventory unit)` (public static) → UNIT_INVALID.
  - `InventSite::exist(site)` → SITE_NOT_FOUND.
  - `InventLocation::find(warehouse)` must exist and, when a site is given, have `InventSiteId == site` → WAREHOUSE_INVALID.

All messages are labels with placeholders, for example "Validation Failed: Customer account '%1' does not exist in legal entity %2."

### 4.5 Creation – class DYLO_SalesOrderApiOrderCreator

`public SalesId create(DYLO_SalesOrderApiRequestContract _request)` runs inside `ttsbegin/ttscommit`.

**Header:**
1. `salesTable.clear(); salesTable.initValue();`
2. `salesTable.SalesId = NumberSeq::newGetNum(SalesParameters::numRefSalesId()).num();`
3. `salesTable.CustAccount = ...; salesTable.initFromCustTable();`
4. Set the header fields:
   - CurrencyCode, when given;
   - PurchOrderFormNum = customerPoReference;
   - ShippingDateRequested = requestedShipDate.
5. `if (!salesTable.validateWrite()) throw error(...)`, then `salesTable.insert()`.

**Each line:**
1. `salesLine.clear(); salesLine.SalesId = salesTable.SalesId; salesLine.ItemId = itemId;`
2. Inventory dimensions: build an InventDim from the site and warehouse and set `salesLine.InventDimId = InventDim::findOrCreate(inventDim).inventDimId`. A site or warehouse that is missing is not set, so the defaults apply.
3. `salesLine.SalesQty = qty;` and `salesLine.SalesUnit = unit` when a unit is given.
4. `salesLine.ShippingDateRequested = requestedShipDate;`
5. `salesLine.createLine(true, true, true, true, true, true)` (public method of SalesLine). It validates, initialises from the order and the item, calculates the inventory quantity, and searches markup and price.
6. When a price override is given: `salesLine.SalesPrice = unitPrice; salesLine.PriceUnit = 1; salesLine.LineAmount = salesLine.calcLineAmount(); salesLine.update();`

**Errors:** any failure rolls back the whole order. The processor catches the exception and turns the infolog lines written since the call started into messages, with code CREATE_FAILED.

All the methods used are public members of SalesTable, SalesLine, NumberSeq and InventDim. No standard method is wrapped, so no Chain of Command is needed.

### 4.6 Logging and formatting

**DYLO_SalesOrderApiTraceLogger:**
- `logCall(...)` inserts a trace record.
- `logRetry(DYLO_SalesOrderApiTrace _trace, response, duration)` updates the record after a reprocess.
- It runs outside the order transaction: the processor has already committed or aborted, so a failed order still leaves its trace.

**DYLO_JsonFormatter:**
- `static str format(str _json)` is a plain X++ pretty-printer that uses no external library.
- It walks the characters and tracks whether it is inside a string, including escapes.
- It indents 2 spaces after `{`/`[` and before `}`/`]`, adds a line break after `,`, and adds a space after `:`.

### 4.7 Reprocessing – class DYLO_SalesOrderApiReprocess

The class has a `main(Args)` and is called from an action menu item, with the data source record DYLO_SalesOrderApiTrace.

1. Re-reads the record for update and checks `canReprocess()`.
2. Deserializes `RequestJson` with `FormJsonSerializer::deserializeObject(classNum(DYLO_SalesOrderApiRequestContract), RequestJson)`.
3. Times the call and runs `DYLO_SalesOrderApiProcessor::process` inside `changecompany` of the record's company.
4. Calls `logRetry`. Retry Count goes up by 1, and LastRetryDateTime, LastRetryBy, ResponseJson, ErrorCode and ErrorMessage are replaced.
   - On success: Status = Reprocessed and SalesId is set.
   - On failure: Status stays Failed.
5. Shows an info or warning message and refreshes the caller's data source with `FormDataUtil::getFormDataSource(...).research(true)`.

### 4.8 Purge – SysOperation

- **DYLO_SalesOrderApiPurgeContract** has one member, RetentionDays (int), default 90. Its validate requires a value of at least 1.
- **DYLO_SalesOrderApiPurgeController** extends SysOperationServiceController.
  - It calls `DYLO_SalesOrderApiPurgeService.purge`.
  - From the form it runs Synchronous by default, and it can be batched.
  - Its caption is "Purge old sales order API logs".
- **DYLO_SalesOrderApiPurgeService** extends SysOperationServiceBase.
  - `purge(contract)` runs `delete_from trace where trace.Status == DYLO_SalesOrderApiStatus::Success && trace.ExecutedDateTime < DateTimeUtil::addDays(DateTimeUtil::utcNow(), -RetentionDays)`.
  - It reports the number of rows deleted.

## 5. Setup and data

1. In System administration > Setup > Microsoft Entra ID applications, register each external system's client ID and map it to a D365 user.
2. Give that user the roles **DYLO_SalesOrderApiIntegrationUser** and **Sales clerk**, or your own sales order role. Make sure its default company is right, or have the caller send `legalEntity`.
3. Assign **DYLO_SalesOrderApiSupport** or **DYLO_SalesOrderApiAdministrator** to the support users.
4. Optionally, schedule *Purge old sales order API logs* as a recurring batch job.
5. The sales order number sequence must be set up (standard).
