The design adds a new form *Product information management > Setup > Categories and attributes > Merchandising hierarchy*. It shows the hierarchy as a tree on the left and the selected node's details on the right. Below the details is a grid of released products assigned to the node and its sub-nodes. The hierarchy and product assignments are kept per legal entity. When a trade agreement journal with sales prices is posted, each price line for an item in the hierarchy is checked against the item's active cost price. If the gross margin is below the node's effective minimum, a warning is shown and posting continues.

## 2. Scope and assumptions

In scope: new tables, form, dialog, classes, menu entries, security and labels described in section 4; one Chain of Command extension on trade agreement journal posting.

Out of scope (as the client answered: check only when trade agreement journals are posted): margin checks on sales order / quotation lines, on the released product's default sales price, or on the trade agreement journal "Validate" button. Reporting on the hierarchy beyond the form.

Decisions taken from the client's answers:
- Margin enforcement is a **warning only**; the user can continue and the journal is posted.
- The cost used is the item's **active cost price** on the released product.
- A released product is on **one node only**; hierarchy and assignments are **per legal entity**.
- Category Manager and Target Margin % are built; Target Margin % is the node's inherited threshold.
- The screen uses the **standard D365 look** and is titled **"Merchandising hierarchy"**.

Assumptions (correct them if they are wrong):
1. **Blank margin = 0.** A Minimum Gross Margin % of 0 (blank) means "inherit from the nearest parent". A node therefore cannot set an explicit 0 % under a parent that has a threshold. The root node's 0 means "no threshold".
2. **One root per legal entity.** The form creates a root node "ROOT – All commercial products" automatically the first time it is opened in a legal entity. The root is level 1, its children level 2, and so on (as in the mockup, "100 – Home Audio Systems (Level 2)"). The root cannot be moved or deleted.
3. **Leaf nodes only.** Products can only be assigned to a node without child nodes. A node that already has products cannot get a child node or receive a re-parented node until its products are moved.
4. **Delete guard covers all child nodes.** A node cannot be deleted while it has **any** child node (active or inactive) or any assigned product. This follows AC-04.
5. **Inactive nodes.** An inactive node cannot receive new products or new child nodes. Its threshold still applies to products already assigned to it and is still inherited by its children.
6. **Product grid content.** The grid shows the products assigned to the selected node **and all its sub-nodes**, as in the mockup: node 120 shows products and a roll-up count of 18. "Roll-up count" is the number of products assigned to the node and all its sub-nodes. "Target Margin %" is the effective (inherited) minimum margin of the node the product is assigned to. "Status" is the released product's **product lifecycle state**.
7. **Margin check rules.**
   - The check covers trade agreement journal lines of type *Price (sales)* for a single item (*Item code = Table*). Lines for item groups or all items, discounts, and purchase prices are not checked.
   - Gross margin % = (unit sales price − unit cost) / unit sales price × 100.
   - Unit sales price = line Amount / Price unit. It is converted to the item's inventory unit, and from the line currency to the company's accounting currency at the line's From date (today if blank).
   - Unit cost = the item's **active cost price**, the same figure "Manage costs > Item price" shows: the active cost price (InventItemPrice, type Cost) for the line's dimensions at the line's From date. When no active cost price exists, the cost price on the released product's Inventory setup (InventTableModule) is used.
   - Misc. charges on the line are ignored. A line with zero or negative price is reported as below margin. An item not in the hierarchy, or whose node threshold is 0, is not checked.
8. **Form look.** The form uses standard D365 form controls and theme. The tree, the details and the product grid are arranged as in Figure 1. The mockup's dark header bar is the standard D365 navigation bar; its title "Commercial Catalog Hierarchy" becomes the form caption **"Merchandising hierarchy"**. The mockup's dark-blue colours, fonts and pixel positions are not reproduced (confirmed by the client).
9. **Re-parenting** is done with a button and a dialog, not by drag and drop.
10. **Category Manager** is an employee (worker) record of D365 Human resources.

## 3. Functional design

### 3.1 Merchandising hierarchy form
Menu: *Product information management > Setup > Categories and attributes > Merchandising hierarchy*.

- **Left pane – tree.** On opening, the form loads the root node and expands it one level. Expanding a node loads its children, ordered by their sort order. Each node shows "Node ID – Name". Inactive nodes are shown with "(inactive)" after the name.
- **Right pane – node details** for the selected node:
  - Node code and Name.
  - Parent node, shown as "100 – Home Audio Systems (Level 2)".
  - Level (read-only).
  - Minimum gross margin % (own value; 0 = inherit).
  - Effective minimum gross margin % and Inherited from node (read-only).
  - Category manager and Active.
- **Assigned released products** (below the details). The heading shows "Assigned released products (Roll-up count: N products)". The grid shows Item ID, Product name, Node, Target margin % and Status. Buttons **Add product** (only when the selected node is an active leaf) and **Remove product**.
- **Action pane:**
  - **New child node** creates a node under the selected node with level = parent + 1 and sort order = last + 1. Blocked if the selected node has products or is inactive.
  - **Move up / Move down** swap the sort order with the previous / next sibling.
  - **Re-parent node** opens a dialog to choose the new parent. The selected node cannot be placed under itself or any of its descendants (AC-02), under a node that has products, or under an inactive node.
  - **Delete node** is blocked while the node has child nodes or products (AC-04).
- **Inheritance (AC-03).** Changing a node's Minimum gross margin %, or re-parenting it, immediately recalculates the effective threshold and the level of that node and all its descendants. Descendants with their own value keep it and pass it down to their own children.

### 3.2 Product assignment
A released product can be assigned to one node per legal entity. Assigning it to a second node is refused with a message that names the node it is already on. Deleting a released product removes its assignment.

### 3.3 Margin warning on trade agreement posting
When a trade agreement journal is posted (Price/discount agreement journal > Post, interactively or in batch), each checked line (see assumption 7) whose gross margin is below the effective minimum of the item's node produces a warning in the posting log:

> Item A0012, valid from 01/12/2026, account Table/US-001: gross margin 21.40 % is below the minimum 28.00 % of merchandising node 120 – Studio Monitors.

Posting then continues as normal; the trade agreement is created.

Methods:

- `initFromParent(DYLO_MerchHierarchyNode _parent)` sets ParentNode, HierarchyLevel = parent + 1, SortOrder = `DYLO_MerchHierarchyManager::nextSortOrder(parent)`, and EffectiveMinGrossMarginPct / InheritedFromNode from the parent.

### 4.3 Business logic

**Class `DYLO_MerchHierarchyManager`** (new; all static). It holds all recursive logic:
- `validateNewParent(DYLO_MerchHierarchyNode _node, DYLO_MerchHierarchyNode _newParent)` returns false with the error "Node %1 cannot be moved under %2 because %2 is one of its own descendants." It walks *upwards* from `_newParent` via ParentNode until 0 and fails if it meets `_node.RecId`. It also fails if `_newParent` = `_node`, has products, or is inactive. A guard of 1000 steps stops a corrupted loop.
- `recalcSubtree(DYLO_MerchHierarchyNode _node)` (recursive, inside the caller's transaction). For each child of `_node` (`select forupdate ... where ParentNode == _node.RecId`):
  - HierarchyLevel = `_node.HierarchyLevel` + 1;
  - if the child's MinGrossMarginPct ≠ 0, Effective = own and InheritedFromNode = child;
  - otherwise Effective = `_node.EffectiveMinGrossMarginPct` and InheritedFromNode = `_node.InheritedFromNode`;
  - `doUpdate()` so that the table's `update()` does not recurse twice, then recurse into the child.
- `reparent(DYLO_MerchHierarchyNode _node, RecId _newParentRecId)`, in `ttsbegin`/`ttscommit`: validate; set ParentNode, SortOrder = `nextSortOrder(newParent)`, level and effective margin from the new parent; `update()`, which triggers `recalcSubtree`.
- `moveUp(_node)` / `moveDown(_node)` find the previous / next sibling by SortOrder and swap the two SortOrder values in one transaction. They do nothing at the edge.
- `nextSortOrder(_parent)` returns max(SortOrder) + 1 among the parent's children.
- `subtreeNodeRecIds(RecId _node)` returns a Set of the node and all its descendants (recursive). `rollupProductCount(RecId _node)` counts DYLO_MerchHierarchyProduct records whose Node is in that set.
- `createRootIfMissing()` creates the root node: NodeId "ROOT", Name "All commercial products", level 1, effective margin 0.

**Class `DYLO_MerchHierarchyTreeDatasource extends CcFormTreeDatasource`** (new). `CcFormTreeDatasource` (PersonnelCore) is public and not final; it is the helper the standard `MCRCustCategoryHierarchy` form uses (through `MCRCustCategoryTreeDatasource`).
- The constructor calls `super(_formDataSource, _tree, fieldNum(DYLO_MerchHierarchyNode, RecId), fieldNum(DYLO_MerchHierarchyNode, ParentNode), fieldNum(DYLO_MerchHierarchyNode, Name), false, false, fieldNum(DYLO_MerchHierarchyNode, NodeId), fieldNum(DYLO_MerchHierarchyNode, SortOrder))`.
- `itemText` is overridden to return "NodeId – Name", plus " (inactive)" when Active = No.
- `create()` is overridden: it refuses when the selected node may not get children, calls `initFromParent`, and selects the new item.
- `delete()` is overridden: it runs `validateDelete()` before removing the tree item.
- Drag and drop methods keep the base behaviour (not used).
- `refreshSubtree(int _idx)` rebuilds a branch after a move or re-parent, using `buildSubTree(_idx, value, true)`.
- `MCRCustCategoryTreeDatasource` is the reference for these overrides.

**Class extension `PriceDiscAdmCheckPost_DYLO_Extension`** (`[ExtensionOf(classStr(PriceDiscAdmCheckPost))]`). It wraps **`protected void createOrUpdatePriceDiscTableRecords()`** (verified in the standard source: protected, not final, no Hookable/Wrappable(false)). It is called only when the journal is really posted, inside the posting transaction, interactively and in batch.
- **Before** `next createOrUpdatePriceDiscTableRecords()`, it calls `DYLO_MerchMarginCheck::construct().checkJournal(journalNum)`. `journalNum` is a class member of `PriceDiscAdmCheckPost`, readable from the extension.
- The check only writes `warning()`, never throws, so posting continues (client's answer: warn and allow to continue).
- `run()` / `postJournal()` are not changed. (`postJournalPost` is private and cannot be wrapped, which is why its protected callee is used.)

**Class `DYLO_MerchMarginCheck`** (new). Read-only; changes no standard data.
- `checkJournal(PriceDiscJournalNum _journalNum)` reads `PriceDiscAdmTrans` where JournalNum == _journalNum, Relation == PriceType::PriceSales and ItemCode == TableGroupAll::Table, exists-joined to `DYLO_MerchHierarchyProduct` on ItemId == ItemRelation.
- For each line:
  1. `node` = the item's node; `threshold` = node.EffectiveMinGrossMarginPct; skip when 0.
  2. `unitPrice` = Amount / (PriceUnit ? PriceUnit : 1).
  3. If UnitId ≠ the item's inventory unit (`InventTableModule::find(item, ModuleInventPurchSales::Invent).UnitId`), convert with `EcoResProductUnitConverter::convertForReleasedProduct(item, line.InventDimId, 1, UnitOfMeasure::unitOfMeasureIdBySymbol(inventUnit), UnitOfMeasure::unitOfMeasureIdBySymbol(line.UnitId))` (sales units per inventory unit) and multiply.
  4. `priceDate` = line.FromDate, or today. unitPriceMST = `CurrencyExchangeHelper::amountCur2MST(unitPrice, line.Currency, 0, priceDate)`.
  5. `unitCost` = active cost price: `InventItemPrice::findCurrent(item, CostingVersionPriceType::Cost, line.InventDimId, priceDate).pcsPrice()`. If none is found, `InventTableModule::find(item, ModuleInventPurchSales::Invent).pcsPrice()` (or Price / PriceUnit if `pcsPrice` is not available in 10.0.48).
  6. `marginPct` = unitPriceMST > 0 ? (unitPriceMST − unitCost) / unitPriceMST × 100 : −100.
  7. If marginPct < threshold, `warning(strFmt("@DYLOExtensions:MarginBelowMinimum", item, priceDate, accountText, round(marginPct, 0.01), threshold, nodeDisplay))`, accountText = AccountCode + "/" + AccountRelation.
- `calcMarginPct(PriceDiscAdmTrans)` is public for unit tests.

## 5. Setup and data
1. System administration > Security configuration: assign role **Merchandising category manager** to category managers and data stewards, or add duty *DYLO_MerchHierarchyMaintain* (maintain) or *DYLO_MerchHierarchyInquire* (view) to existing roles such as the product information manager and pricing roles.
2. In each legal entity, open *Merchandising hierarchy*. The root is created automatically. Build the nodes, set the minimum margins and assign products.
3. Make sure items in the hierarchy have an active cost price (Released products > Manage costs > Item price) or a cost price on the Inventory setup. Otherwise a cost of 0 is used and every price passes the check.

No data migration and no number sequence.
