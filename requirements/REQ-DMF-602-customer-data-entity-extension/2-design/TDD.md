## 1. Summary

**What you asked for and what this design delivers**

| Feature named in the requirement | This design |
|---|---|
| New field Loyalty Tier on the customer (Standard, Silver, Gold, Platinum; default Standard) | Built |
| New field Preferred Delivery Window on the customer (text, up to 50 characters) | Built |
| New group "Commercial Preferences" on the Sales order defaults FastTab of the customer details screen, view and edit | Built |
| Both fields on the Customers V3 data entity and its staging table, for Data management import/export (CSV, Excel, XML) | Built |
| Both fields in OData `/data/CustomersV3` (GET, POST, PATCH) | Built |
| A blank, empty or omitted Loyalty Tier becomes Standard on Data management import and OData creation | Built. This includes an OData call that sends an empty text `""`, as you confirmed. |
| An unknown Loyalty Tier value rejects the row with a clear error and does not change the customer | Built, with our own error message that names the value and lists the allowed values |

Two new fields are added to the customer master table (CustTable). They appear in a new group, **Commercial Preferences**, on the **Sales order defaults** FastTab of the All customers details screen. On the customer, Loyalty Tier is a selection list (enum) whose first value is Standard.

The same two fields are added to the standard **Customers V3** data entity (`CustCustomerV3Entity`, OData collection `CustomersV3`) and its staging table (`CustCustomerV3Staging`). This version follows your answer that the CRM may send an empty Loyalty Tier. In the entity, Loyalty Tier is therefore received as **text** and turned into the list value by our own code:
- empty or blank becomes Standard;
- Standard, Silver, Gold and Platinum are accepted, in any upper or lower case;
- anything else is rejected with our own message, and the customer is not changed.

Everything is built with extensions in the new model DYLOExtensions. No standard object is overlayered.

## 2. Scope and assumptions

**In scope:** the CustTable fields, the customer details screen, the Customers V3 entity and staging, the Loyalty Tier conversion and check, labels, and the new model.

**Out of scope:** other customer entities (Customers V2, Customer details V2, CDS dual-write maps), reports, and logic that uses the loyalty tier (pricing, discounts, delivery scheduling). Nothing in the FRD asks for these.

**Assumptions** (the build goes ahead on these. Please correct any that are wrong):

- **A1 – Existing customers become Standard.** When the change is deployed, every existing customer shows Loyalty Tier = Standard and an empty Preferred Delivery Window until the CRM or a user updates them. No separate data update is run.
- **A2 – An empty Loyalty Tier sets Standard, also for existing customers.** The rule is the same for every channel:
  - A blank Loyalty Tier cell in a Data management import sets Standard on new customers and also on existing ones.
  - An OData POST or PATCH that sends `"LoyaltyTier": ""` (or `null`) sets Standard on new customers and also on existing ones.
  - So if an existing customer is Gold and the CRM sends an empty value, that customer becomes Standard.
  - To leave an existing customer's tier unchanged, the CRM leaves the property out of the OData PATCH, or the Loyalty Tier column is left out of the Data management file and mapping.
  - An OData POST that leaves the property out creates the customer as Standard.
- **A3 – Accepted values.** Import files and OData accept `Standard`, `Silver`, `Gold` and `Platinum`, in any upper or lower case, with spaces around them ignored. The screen labels are the same words in en-US. Export and OData GET return the value names with a capital first letter (for example `Gold`).
- **A4 – Error message for an unknown value.** A value such as `Diamond` is rejected with the message *"Loyalty Tier value 'Diamond' is not valid. Allowed values are Standard, Silver, Gold and Platinum."*
  - In Data management, the row is marked as an error in the execution log with this message. The other rows still import. The customer on that row is not changed, not even its other fields.
  - In OData, the request fails with an error response that carries the same message, and the customer is not changed.
- **A5 – Loyalty Tier is plain text in OData and in the files.** In OData metadata, `LoyaltyTier` is now a text property (up to 20 characters), not a typed list. The CRM payload in Figure 1 (`"LoyaltyTier": "Gold"`) works unchanged.
- **A6 – Preferred Delivery Window is free text.** Its format (for example `08:00 AM - 12:00 PM`) is not checked. Text longer than 50 characters is cut off by Data management, as for every other text field. OData rejects it.
- **A7 – Field names in integrations.** The entity and OData field names are exactly `LoyaltyTier` and `PreferredDeliveryWindow`, as in the FRD's JSON payload. The table columns carry the prefix (`DYLO_LoyaltyTier`, `DYLO_PreferredDeliveryWindow`).
- **A8 – Security.** Users who can already view or edit customers, or use the Customers V3 entity, can view or edit the new fields. The new fields carry no separate permission.
- **A9 – Figure 1 is a design diagram, not a screen layout.** The left panel shows where the group goes: on the Sales order defaults FastTab, after Site, Warehouse and Pool. The following are explanations only and are not built: the sample customer "US-004 Cave Wholesales", the sample values, the red dashed frame, the arrows and the right-hand flow diagram. The group uses the standard look of the customer screen, not the pink box.

## 3. Functional design

### 3.1 Customer details screen (Accounts receivable > Customers > All customers > customer)
On the **Sales order defaults** FastTab, a new group **Commercial Preferences** is placed directly after the standard sales order group that holds Site, Warehouse and Pool, as in Figure 1. It contains:

| Field | Control | Behaviour |
|---|---|---|
| Loyalty Tier | Drop-down: Standard, Silver, Gold, Platinum | New customers start as Standard. Editable in edit mode. |
| Preferred Delivery Window | Text, up to 50 characters | Optional free text, editable in edit mode. |

### 3.2 Data management (Customers V3 entity)
- After deployment and **Refresh entity list**, the Customers V3 entity shows the source fields **LOYALTYTIER** and **PREFERREDDELIVERYWINDOW**.
- New projects map them automatically. Existing projects map them when the mapping is regenerated (see section 5).
- **Export:** both fields are exported with the customer's current values. Loyalty Tier is exported as `Standard`, `Silver`, `Gold` or `Platinum`.
- **Import:** both fields are written to the customer.
  - A blank Loyalty Tier gives Standard (A2).
  - An unknown value marks the row as an error with our message and leaves the customer unchanged (A4).

### 3.3 OData (`/data/CustomersV3`)
- **GET** returns `LoyaltyTier` as text (for example `"Gold"`) and `PreferredDeliveryWindow`.
- **POST** creates the customer with both values. If `LoyaltyTier` is omitted, empty `""` or `null`, the customer is created as Standard.
- **PATCH** updates only the properties sent. A `LoyaltyTier` of `""` or `null` sets Standard. A PATCH without `LoyaltyTier` leaves the tier unchanged.
- An unknown value returns an error with our message, and the customer is not changed.
- Existing CRM payloads that do not send the new properties work as before.

## 4. Technical design

All objects go in model **DYLOExtensions**. No overlayering is used.

On CustTable, Loyalty Tier is an enum whose element 0 is Standard, so new customers and the form default to Standard. On the entity, `LoyaltyTier` is an unmapped (virtual) **string** field. Text cannot be rejected before our code runs, so an empty value reaches our code and becomes Standard instead of being refused by OData.

A Chain of Command extension of `CustCustomerV3Entity` does two things:
- converts the text to the enum when the entity writes to CustTable;
- fills the text from the enum when the entity is read.

The developer's skills **d365-label-files** (labels) and **d365-forms** (form extension) apply.

Standard code checked (CustCustomerV3Entity, ApplicationSuite\Foundation, read in 10.0.49):
- `public class CustCustomerV3Entity`. It is not final and not internal.
- `public void mapEntityToDataSource(DataEntityRuntimeContext, DataEntityDataSourceRuntimeContext)`. It handles data source `CustTable`, then calls `super()`.
- `public void postLoad()`.
- Both methods are public, are not final and carry no Hookable/Wrappable(false) attribute, so they can be wrapped.
- The entity is public (`PublicEntityName` CustomerV3, `PublicCollectionName` CustomersV3, staging `CustCustomerV3Staging`) and has a data source named `CustTable`.

### 4.6 Class – `DYLO_CustCustomerV3Entity_Extension` (Chain of Command, `[ExtensionOf(tableStr(CustCustomerV3Entity))]`, final class)

**`mapEntityToDataSource(DataEntityRuntimeContext _entityCtx, DataEntityDataSourceRuntimeContext _dataSourceCtx)`** – wraps the standard method.
- Before `next`: when `_dataSourceCtx.name() == dataEntityDataSourceStr(CustCustomerV3Entity, CustTable)`, and `this.fieldState(fieldNum(CustCustomerV3Entity, LoyaltyTier)) != FieldState::NotSet` (the caller sent the field):
  1. `DYLO_LoyaltyTier tier = DYLO_CustLoyaltyTierConverter::fromText(this.LoyaltyTier);` This throws an error on an unknown value (see 4.7).
  2. `CustTable custTable = _dataSourceCtx.getBuffer(); custTable.DYLO_LoyaltyTier = tier;`
- When the field was not sent, nothing is set. A new CustTable stays at its default, Standard, and an existing customer keeps its tier (A2).
- Then call `next mapEntityToDataSource(_entityCtx, _dataSourceCtx);`.
- The conversion runs before `next`, so an unknown value stops the write before anything is saved. In Data management, the staging-to-target step for that row runs in its own transaction, so the row is logged as an error and the customer is untouched. In OData, the whole request is rolled back.

**`postLoad()`** – wraps the standard method.
- After `next postLoad();`, set `this.LoyaltyTier = DYLO_CustLoyaltyTierConverter::toText(this.<CustTable tier>)`.
- The tier is read with `CustTable::find(this.CustomerAccount)` inside `changecompany(this.DataAreaId)`. The entity has the field `CustomerAccount` and no CustTable RecId field. If no record is found, the code returns `Standard`.
- Data management export and OData GET then return `Standard`, `Silver`, `Gold` or `Platinum`.
- Data management runs an export row by row when an entity has virtual fields, so `postLoad` fills the column in exports too. Test T3 checks this.

### 4.7 Class – `DYLO_CustLoyaltyTierConverter` (new, final class, static methods)
| Method | Logic |
|---|---|
| `public static DYLO_LoyaltyTier fromText(DYLO_LoyaltyTierText _text)` | `str value = strLRTrim(_text);` If `value == ''`, return `DYLO_LoyaltyTier::Standard`. Otherwise, loop over the elements of `enumNum(DYLO_LoyaltyTier)` with `DictEnum`. If `strUpr(value)` equals `strUpr(index2Symbol(i))` or `strUpr(index2Label(i))`, return that value. If nothing matches, `throw error(strFmt("@DYLOExtensions:DYLO_LoyaltyTierInvalid", value));` |
| `public static DYLO_LoyaltyTierText toText(DYLO_LoyaltyTier _tier)` | Return `enum2Symbol(enumNum(DYLO_LoyaltyTier), enum2int(_tier))` (`Standard`, `Silver`, `Gold`, `Platinum`). |

The rules are covered as follows:

| Rule from the FRD and the client's answer | How it is met |
|---|---|
| Blank Loyalty Tier on DMF import becomes Standard | The staging value is empty, `fieldState` is Set, so `fromText` returns Standard. |
| Empty `""` or `null` on OData POST or PATCH becomes Standard | `fieldState` is Set and the text is empty, so `fromText` returns Standard. |
| Omitted Loyalty Tier on OData POST becomes Standard | `fieldState` is NotSet, so the new CustTable stays at its default, Standard. |
| Omitted on OData PATCH | `fieldState` is NotSet, so the existing tier is unchanged. |
| Unknown Loyalty Tier rejects the row | `fromText` throws our labelled error. The DMF row goes to error with the message, and OData returns an error. CustTable is untouched. |
| New customer on the form | Enum element 0 = Standard. |

### 4.8 Staging – `CustCustomerV3Staging.DYLOExtensions` (table extension of CustCustomerV3Staging, ApplicationSuite\Foundation)
| Field | Type | Properties |
|---|---|---|
| `LoyaltyTier` | EDT `DYLO_LoyaltyTierText` (string) | Mandatory = No |
| `PreferredDeliveryWindow` | EDT `DYLO_PreferredDeliveryWindow` | Mandatory = No |

- The field names must be exactly the entity field names, so that the entity-to-staging mapping is automatic.
- Loyalty Tier is text in staging, so any value in the file, including an unknown one, reaches staging. It is then checked by our code on the way to the customer.
- Do not regenerate the staging table. Extend it by hand.

### 4.9 Security
No new duty, privilege or role:
- Table fields added to CustTable fall under the existing CustTable form privileges (for example `CustTableMaintain` / `CustTableView`).
- Entity fields fall under the existing Customers V3 entity privileges.
- The new classes are called only from the entity and need no privilege.

Test T7 checks this.

## 5. Setup and data
1. Deploy the package to the environment and run a database sync.
2. In **Data management > Framework parameters > Entity settings**, select **Refresh entity list**.
3. In each existing import or export project that uses **Customers V3**, open **View map** and select **Generate source mapping**, or map LOYALTYTIER and PREFERREDDELIVERYWINDOW by hand. New projects map them automatically.
4. Add the columns `LOYALTYTIER` and `PREFERREDDELIVERYWINDOW` to the CRM export files and templates. For OData, add `LoyaltyTier` and `PreferredDeliveryWindow` to the payload. If the CRM generates its client from the OData metadata, it should refresh it: `LoyaltyTier` is a text property (A5).
5. No other setup is needed, and no data migration: existing customers start as Standard (A1).

## 7. Open questions
None.

The previous question about an empty Loyalty Tier from the CRM is answered: an empty value means Standard. The design now accepts and defaults it (sections 4.5–4.7). As a result, Loyalty Tier is a text property in OData (A5), and the error for an unknown value is our own message (A4).
