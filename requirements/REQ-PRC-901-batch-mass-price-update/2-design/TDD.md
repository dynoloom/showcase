# TDD – REQ-PRC-901 Periodic mass trade agreement price update (batch)

*Version 2. Changed from version 1: you confirmed that, when Auto-post is off, the old prices end only when someone posts the journal. That rule is now part of the design (3.2, 3.3) and is no longer an open question. Test T12 is new. Nothing else has changed.*

## 1. Summary

**What you asked for and what this design delivers**

| Feature named in the requirement | This design |
|---|---|
| Batch dialog with these fields: Journal name, Item group (several can be chosen), Customer price group, Adjustment %, Effective from date, Rounding rule (Nearest 0.05 / 0.10 / Exact), Auto-post | Built |
| Selection of active sales price agreements for the chosen item groups and customer price group | Built |
| Old agreements end the day before the effective date, and new agreement lines are created at the adjusted price in a Price/discount agreement journal | Built. Both are done through the standard journal, so the old prices end when the journal is posted (see 3.3) |
| Multi-threaded batch: items split into task bundles of a size you set (default 500) | Built |
| Optional automatic posting of the journal | Built (the standard journal posting runs) |
| Completion Infolog: lines processed, journal number, items skipped because their records were locked | Built |
| Validation: block 0 % and an invalid journal name (AC-01) | Built |
| Menu item: Sales and marketing > Periodic tasks > Mass trade agreement price update | Built |

The new periodic job is a SysOperation batch job. Each time it runs, it creates one standard Price/discount agreement journal. For every active sales price agreement that matches the filters, the journal gets two lines:
- one line that closes the existing agreement on the effective date minus 1 day;
- one line that creates the new agreement from the effective date, at the adjusted and rounded price.

You can review the journal in the standard Price/discount agreement journals form before posting, or the job posts it for you (Auto-post). As you decided, the existing agreements stay unchanged until the journal is posted. At posting the old agreement is closed and the new price starts in the same step, so there is never a day without a price. Posting is done by the standard posting class `PriceDiscAdmCheckPost`. Standard posting updates the existing agreement (through `PriceDiscTableRef`) and creates the new one, so the job never writes to the trade agreement table `PriceDiscTable` itself.

All objects are new or extensions of standard objects, in the new model **DYLOExtensions**, which is built by extension only.

## 2. Scope and assumptions

**In scope:** sales price agreements (`PriceDiscTable.Relation = PriceType::PriceSales`, module Customer) set up for a **customer price group** (`AccountCode = Group`) and for a single item (`ItemCode = Table`).

**Your decision, now part of the design:** old prices end when the journal is posted, not when the job runs. If Auto-post is off, the existing agreements stay unchanged until someone posts the journal.

**Assumptions (correct us if any is wrong):**
1. **Which agreements count as active.** An agreement is active when its To date is blank or on/after the Effective from date, **and** its From date is before the Effective from date. Agreements that already start on or after the Effective from date (future prices) are **not changed**. They are listed as skipped in the Infolog and the log, because closing them on the day before they start is not possible.
2. **Dates of the new agreement.** The new line starts on the Effective from date. It ends on the old agreement's original To date, so a blank To date stays blank.
3. **What is copied unchanged.** Currency, unit, quantity breaks (from/to), price unit, inventory dimensions, "find next", lead time and price charges are copied from the old agreement unchanged. Only the unit price (`Amount`) is adjusted.
4. **Rounding.** "Nearest 0.05 / 0.10" rounds half up to the nearest 0.05 or 0.10 **in the agreement's own currency**. "Exact" rounds to the currency's normal amount decimals. Example: 100.00 × (1 + 6.5 %) = 106.50, which stays 106.50 at 0.10 (AC-02).
5. **Allowed percentage.** The adjustment percentage may be positive or negative, but not 0 and not −100 % or less. If a new price would come out at 0 or below, that agreement is skipped and logged.
6. **Item group filter left empty means all item groups.** Before the job starts in that case, the dialog warns: "No item group selected – all item groups will be updated". Only one Customer price group can be chosen, and it is required, as the mockup shows.
7. **"Locked records" means two things.** (a) An agreement that is already on a line of another journal that is not posted yet. (b) An item whose update hits a database update conflict or deadlock after 5 retries. Such items or agreements are skipped and named in the Infolog. If something is skipped, the rest of its bundle carries on.
8. **Bundles are set by number of items, not number of tasks.** The bundle size is the number of items per batch task, as the FRD text says. The dialog field is "Items per batch task" and defaults to 500. The mockup's "Multi-Threading Bundles: 4 Tasks" is sample content: the number of tasks follows from the number of items. Batch group and Batch processing are on the standard "Run in the background" tab.
9. **The Rounding rule field is on the dialog**, even though the mockup does not show it, because section 2 of the FRD lists it. It appears under Effective from date.
10. **Dialog layout.** The mockup (FRD section 3, image 1) is used for which fields appear and in what order. The dialog is the standard SysOperation dialog, so the title-bar colours, "Product Information Management" and the sample values (PRC-ADJ, SPEAKERS, WHSL-TIER1, 12/01/2026) are sample content. They are not built.
11. **If no matching agreement is found,** the job stops with a warning and deletes the empty journal it created.
12. **Auto-post posts whatever lines were created,** even if some items were skipped. If posting fails a check, the journal stays unposted with the standard journal log, the old prices stay unchanged, and the Infolog says so.

## 3. Functional design

### 3.1 Menu and dialog
Sales and marketing > Periodic tasks > **Mass trade agreement price update** opens a dialog captioned "Periodic mass trade agreement price adjustment". The fields appear in this order, in a group called **Parameters**:

| # | Label | Type | Required | Values | Lookup |
|---|---|---|---|---|---|
| 1 | Price/discount journal name | PriceDiscJournalName | Yes | one | Price/discount journal names (`PriceDiscAdmName`) |
| 2 | Item group filter | List of ItemGroupId | No (empty = all) | several | multi-select on item groups (`InventItemGroup`) |
| 3 | Customer price group | PriceGroupId | Yes | one | customer price groups only (`PriceDiscGroup`, Module = Customer, Type = Price group) |
| 4 | Adjustment percentage (%) | DYLO_PriceAdjPercent (real, 2 decimals, may be negative) | Yes | one | – |
| 5 | Effective from date | TransDate | Yes | one | date |
| 6 | Rounding rule | DYLO_PriceAdjRoundingRule (Exact / Nearest 0.05 / Nearest 0.10) | Yes (default Exact) | one | enum |
| 7 | Auto-post journal | NoYes | No (default No) | one | checkbox |
| 8 | Items per batch task | Integer | Yes (default 500, minimum 1) | one | – |

Below them comes the standard **Run in the background** tab (Batch processing, Batch group, recurrence, alerts), then OK / Cancel.

**Validation (AC-01).** OK is refused with a clear warning when:
- the journal name is blank or does not exist;
- the adjustment % is 0, or −100 or less;
- the effective date is blank;
- the customer price group is blank or is not a customer price group;
- items per task is less than 1.

### 3.2 Processing
1. A new journal header (`PriceDiscAdmTable`) is created from the chosen journal name. Its number comes from the standard number sequence, and its description is "Mass price update <percent>% from <date>".
2. The job collects the item numbers that have active matching agreements (see assumption 1).
3. **In batch:** the items are split into bundles of "Items per batch task". Each bundle becomes a runtime task of the batch job, and the tasks run in parallel. A final "summary and post" task runs after all bundle tasks have finished. **Not in batch:** the same work runs in one pass, in the user's session.
4. For each item in a bundle, in its own transaction:
   - each matching agreement that is not locked gets two journal lines: (a) a copy of the agreement that points to it (`PriceDiscTableRef`), with To date = Effective from date − 1; (b) a new line with From date = Effective from date, To date = the old To date, and Amount = the adjusted and rounded price;
   - each line is checked with the table's `validateWrite`. If a check fails, the item is skipped and logged.
   - The job itself never changes the agreement. Nothing in the trade agreements changes until the journal is posted.
5. The summary task:
   - writes the Infolog (shown in Batch job history / the batch task log): number of agreements processed, number of journal lines created, the journal number, and every skipped item with its reason;
   - if Auto-post is Yes, it posts the journal through the standard posting. The old agreements are closed and the new prices created at that moment;
   - if Auto-post is No, the Infolog says the journal is waiting to be posted, and that the current prices stay in force until it is posted;
   - the Infolog then says whether the journal was posted, or gives the reason it was not.

### 3.3 Why the expiry goes through the journal (old prices end at posting)
The standard journal posting updates the From and To dates of the agreement a line refers to (`PriceDiscAdmCheckPostPriceDiscTableUpdater`, which matches on `PriceDiscTableRef`). It also inserts new agreements (`PriceDiscTableCopyFromPriceDiscAdmTrans`) and clears the price cache. Both happen in the same posting, so the old agreement ends and the new one starts together, as you asked: there is never a day without a price, whether the job posts the journal or someone posts it later. Using the standard posting also keeps the standard overlap and gap checks and the journal audit trail, and it avoids writing directly to the trade agreement table.

If the journal is posted after the Effective from date, the old agreement is still closed on Effective from date − 1 and the new price applies from the Effective from date. Orders priced between those two dates keep the price they got at the time.

## 4. Technical design

**Model:** `DYLOExtensions` (new, USR layer), labels in label file `DYLOExtensions` (en-US).
**Module references:** ApplicationPlatform, ApplicationFoundation, ApplicationSuite, Directory, Currency (add any further module the compiler asks for).
**Skills:** d365-label-files (all captions); d365-report-parameters (the List-member pattern with `AifCollectionTypeAttribute` and the `SysLookupMultiSelectCtrl` multi-select lookup, applied here to a SysOperation dialog). d365-forms is not needed: no form is created or extended, because SysOperation generates the dialog.

### 4.1 Data model

| Object | Type | Details |
|---|---|---|
| `DYLO_PriceAdjRoundingRule` | Enum | Exact (0), Nearest005 (1), Nearest010 (2); labels "Exact", "Nearest 0.05", "Nearest 0.10" |
| `DYLO_PriceAdjPercent` | EDT real | 2 decimals, allows negative, label "Adjustment percentage (%)" |
| `DYLO_PriceAdjLogStatus` | Enum | Processed, Skipped |
| `DYLO_PriceAdjRunId` | EDT Guid | identifies one run |
| `DYLO_PriceAdjLog` | Table (Transaction, company-specific) | Fields: RunId (DYLO_PriceAdjRunId), JournalNum (PriceDiscJournalNum), ItemId, PriceDiscTableRef (RefRecId), Status (DYLO_PriceAdjLogStatus), Reason (Description255), OldAmount and NewAmount (PriceCur), CurrencyCode. Index RunIdx (RunId, Status). One row per agreement processed or skipped. It is written by the bundle tasks and read by the summary task, because tasks running in parallel cannot share memory. Rows older than 90 days are deleted by the summary task. |

### 4.2 Classes

**`DYLO_TradeAgreementPriceAdjContract`** – data contract (`[DataContractAttribute]`, `[SysOperationContractProcessing(classStr(DYLO_TradeAgreementPriceAdjUIBuilder))]`). It implements `SysOperationValidatable` and has a parm method for each field in 3.1:
- `parmJournalName`
- `parmItemGroupIds`: a `List` of `ItemGroupId`, `[AifCollectionTypeAttribute('return', Types::String)]`
- `parmCustPriceGroup`
- `parmAdjustmentPct`
- `parmEffectiveFromDate`
- `parmRoundingRule`
- `parmAutoPost`
- `parmItemsPerTask` (default 500 in `new`)

Each member gets a `SysOperationDisplayOrderAttribute` and a `SysOperationLabelAttribute`, and all of them are in group "Parameters". `validate()` implements the checks in 3.1.

**`DYLO_TradeAgreementPriceAdjUIBuilder`** – extends `SysOperationAutomaticUIBuilder`.
- `postBuild`: binds the Item group control to a `SysLookupMultiSelectCtrl` on a query over `InventItemGroup` (ItemGroupId, Name).
- Registers a lookup on the Customer price group field over `PriceDiscGroup`, with range Module = `ModuleInventCustVend::Cust` and Type = `PriceGroupType::PriceGroup`.
- `postRun`/`getFromDialog`: writes the selected item groups back into the List.
- Overrides `validate` to show the "all item groups" warning (assumption 6).

**`DYLO_TradeAgreementPriceAdjController`** – extends `SysOperationServiceController`.
- `main` constructs it with service `DYLO_TradeAgreementPriceAdjService.process`, execution mode `ReliableAsynchronous` when batch is chosen, otherwise `Synchronous`.
- `caption()` returns the dialog label; `canGoBatch()` returns true.

**`DYLO_TradeAgreementPriceAdjTaskContract`** – data contract for one runtime task. It holds:
- RunId, JournalNum, the list of ItemIds (`List`), LineNumBase (real);
- the parameters it needs: customer price group, percentage, effective date, rounding rule, auto-post;
- for the summary task, the total number of bundles.

**`DYLO_TradeAgreementPriceAdjTaskController`** – extends `SysOperationServiceController`. It is constructed with method name `processBundle` or `finalizeRun` of the service. These controllers are added as runtime tasks.

**`DYLO_TradeAgreementPriceAdjService`** – extends `SysOperationServiceBase`.
- `process(DYLO_TradeAgreementPriceAdjContract _c)`:
  1. Validates the contract again and creates a new RunId.
  2. Creates `PriceDiscAdmTable` in `ttsbegin`/`ttscommit`: `JournalName` = journal name, `initFromPriceDiscAdmName`, then `insert` (the standard `insert` fetches `JournalNum` from `SalesParameters::numRefPriceDiscJournalNum()`), then `Name`.
  3. Builds the item list with one `select ItemRelation from PriceDiscTable group by ItemRelation` with these ranges:
     - `Module == Cust`, `Relation == PriceType::PriceSales`, `AccountCode == TableGroupAll::GroupId`, `AccountRelation == custPriceGroup`, `ItemCode == TableGroupAll::Table`;
     - `(ToDate == dateNull() || ToDate >= effDate)`;
     - an `exists join InventItemGroupItem` on ItemId / ItemDataAreaId with `ItemGroupId` in the selected groups (no join when the list is empty).
  4. If no items are found, it deletes the journal and gives a warning.
  5. **In batch** (`this.isExecutingInBatch()`):
     - gets `BatchHeader::getCurrentBatchHeader()`;
     - for each bundle of `ItemsPerTask` items, creates a `DYLO_TradeAgreementPriceAdjTaskController` (`processBundle`) with LineNumBase = bundleNo × 1,000,000 and adds it with `addRuntimeTask`;
     - adds one `finalizeRun` task with `addDependency(..., BatchDependencyStatus::FinishedOrError)` on every bundle task, then `batchHeader.save()`.
  6. **Not in batch:** calls `processBundle` for one bundle with all items, then `finalizeRun`.
- `processBundle(DYLO_TradeAgreementPriceAdjTaskContract _t)`. It writes only journal lines (`PriceDiscAdmTrans`) and log rows, and never updates `PriceDiscTable` (the client's rule: old prices end at posting). For each item, inside `try { ttsbegin; … ttscommit; } catch (Exception::Deadlock / UpdateConflict) { retry up to 5, then log as Skipped "Locked" }`:
  - selects the item's matching `PriceDiscTable` records, using the same ranges as step 3 plus `FromDate < effDate`. Records with `FromDate >= effDate` are logged as Skipped "Future agreement";
  - **lock check:** if an `exists join PriceDiscAdmTrans` (PriceDiscTableRef == agreement.RecId) with `PriceDiscAdmTable.Posted == No` and JournalNum != this journal is found, the agreement is logged as Skipped "On unposted journal <num>";
  - computes the new price with `DYLO_TradeAgreementPriceAdjCalc::newPrice(agreement.Amount, pct, rule, agreement.Currency)`. If the result is ≤ 0, the agreement is skipped;
  - **Line A:** `initValue`, `JournalNum`, `initFromPriceDiscTable(agreement)` (this sets PriceDiscTableRef), `ToDate = effDate − 1`, `LineNum = LineNumBase + counter`, then `validateWrite`, then `insert`;
  - **Line B:** same init, then `PriceDiscTableRef = 0`, `FromDate = effDate`, ToDate = the original ToDate, `Amount = newPrice`, next LineNum, then `validateWrite`, then `insert`;
  - writes one `DYLO_PriceAdjLog` row (Processed or Skipped with its reason).

  The line numbers come from a range of their own for each bundle, because `PriceDiscAdmTrans.setNewLineNum` is internal and a `maxof(LineNum)` taken by tasks running in parallel would collide.
- `finalizeRun(DYLO_TradeAgreementPriceAdjTaskContract _t)`:
  - reads `DYLO_PriceAdjLog` for the RunId: counts of Processed and Skipped, the line count from `PriceDiscAdmTrans`, and the journal number;
  - writes `info` lines for the totals and the journal number, and a `warning` per skipped item with its reason;
  - if no lines were created, deletes the empty journal;
  - if AutoPost is set and there are lines, posts: `PriceDiscAdmCheckPostInputContract::construct()`, `parmJournalNum`, `parmCheckActionType(PriceDiscAdmCheckActionType::ValidateAll)`, `parmCheckOnly(false)`, `parmAcceptWarnings(true)`, `parmPriceDiscAdmTransSetSelected(new Set(Types::Int64))`, then `PriceDiscAdmCheckPost::runFromContract(contract.pack())`, then `PriceDiscAdmCheckPostOutputContract::create(...)`;
  - reports `parmIsPosted()`. If it is false, gives a warning that the journal was left unposted and the current prices are unchanged;
  - if AutoPost is not set, gives an `info`: "Journal <num> is ready. Current prices stay in force until the journal is posted."

  All these members are public (checked in ApplicationSuite 10.0.49, `PriceDiscAdmCheckPost`, lines 907–1190), so nothing is wrapped or overlayered.

**`DYLO_TradeAgreementPriceAdjCalc`** – static `newPrice(Price _old, real _pct, DYLO_PriceAdjRoundingRule _rule, CurrencyCode _cur)`:
- computes `raw = _old * (1 + _pct/100)`;
- Exact: `CurrencyExchangeHelper::amount(raw, _cur)` (the currency's amount rounding);
- Nearest005: `round(raw, 0.05)` (half up);
- Nearest010: `round(raw, 0.10)`.

Unit-tested with AC-02 (100, 6.5, Nearest010 gives 106.50).

## 5. Setup and data
1. Check that a Price/discount journal name exists for sales (for example PRC-ADJ): Sales and marketing > Setup > Price/discount > Journal names. Also check that the number sequence for price/discount journals is set in Sales and marketing parameters.
2. Optional: create a batch group (for example PERIODIC-HEAVY) and assign batch servers to it (System administration > Setup > Batch group).
3. Assign the duty "Maintain mass trade agreement price update" to any role other than Sales manager that needs it.
4. When Auto-post is off, post the journal **before** the Effective from date (Sales and marketing > Price/discount > Price/discount agreement journals). Until then, the current prices stay in force.
